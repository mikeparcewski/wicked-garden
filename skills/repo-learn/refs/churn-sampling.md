# Churn sampling — the bounded, top-N git-log method

Estate does **not** rank git churn: `RankHotspots` is structural PageRank over
Calls+Imports edges, blind to history. Temporal ranking is this phase's job, and
it is a git-log method — but a *disciplined* one. The failure mode to design out:
a naive `git log --name-only` over a long history streams megabytes, blows the
worker's ~25K-char output cap (estate agent-behavior R4), and starves the phases
that actually matter. Every recipe below is **bounded** — an explicit top-N cap
plus a sampling rule keyed to history size.

## The three invariants

1. **Cap the output.** The list you keep is always `head -N` (default **40**).
   The raw `--name-only` stream is consumed *inside the shell pipe* (`sort | uniq
   | sort | head`); only the final ≤N rows reach your context. Never `cat` or echo
   the full stream.
2. **Cap the input.** Above a commit threshold (default **2000**) you MUST sample
   or window — never `git log` the full history unbounded. Bound it even when you
   think it's small; size it first and find out.
3. **Two signals, not one.** Churn alone over-weights churny-but-shallow files
   (config, generated). The output of this phase is an *input* to the cross-
   reference against structural hotspots (SKILL.md § Cross-reference), never a
   standalone verdict.

## Step 0 — size the window (bounded probe, no materialization)

Count commits in the window without listing them, and count tracked files for the
rollup decision:

```bash
WINDOW="12.months"                                   # default; override per ask
C=$(git rev-list --count --since="$WINDOW" HEAD)     # commits in window
F=$(git ls-files | wc -l)                            # tracked files
echo "commits_in_window=$C tracked_files=$F"
```

`git rev-list --count` is O(commits) but materializes nothing — safe on any
history. Choose the mode from `C`:

| `C` (commits in window) | Mode | Recipe |
|-------------------------|------|--------|
| `C ≤ 2000`              | **full-scan** | § Full-scan churn |
| `C > 2000`              | **sampled**   | § Sampled churn (pick a strategy) |

And choose granularity from `F`:

| `F` (tracked files) | Granularity |
|---------------------|-------------|
| `F ≤ 5000`          | file-level (default) |
| `F > 5000`, or file-level top-N is dominated by single-change files | **directory rollup** (§ Directory rollup) |

Thresholds are defaults, not laws — a repo with enormous commits (vendored blobs)
may warrant a lower cap; a tiny repo with a 5-year window may stay full-scan above
2000. State the mode you picked and why.

## Full-scan churn (small histories, `C ≤ 2000`)

```bash
git log --since="$WINDOW" --no-renames --name-only --pretty=format: -- . \
  | grep -v '^$' \
  | grep -Ev '(^|/)(node_modules|dist|build|target|vendor|\.min\.|package-lock\.json|Cargo\.lock|pnpm-lock\.yaml|yarn\.lock)(/|$)' \
  | sort | uniq -c | sort -rn \
  | head -40
```

- `--no-renames` (git's default; stated for intent) — do **not** `--follow`
  (per-path only, incompatible with a whole-tree scan).
- `--pretty=format:` empties the commit-header lines so only file paths remain;
  `grep -v '^$'` drops the blank separators.
- The two `grep -Ev` filters strip generated/vendored/lockfile noise — churn there
  is not active *development*. Extend the pattern per repo (e.g. `__generated__`,
  `.pb.go`, `migrations/` if autogenerated).
- `sort | uniq -c | sort -rn | head -40` = count per path, most-changed first,
  top-N capped. This is the whole method for small histories.

Output rows are `<count>  <path>`. That ranked list is phase 1's product.

## Sampled churn (large histories, `C > 2000`)

Pick ONE strategy. Both keep the *input* bounded; the output cap (`head -40`) is
unchanged.

### Strategy A — recency cap (default)

Most-recent-N commits. Recent churn is the better signal for "active areas", and
it's a single git call:

```bash
git log --since="$WINDOW" --no-renames --name-only --pretty=format: --max-count=2000 -- . \
  | grep -v '^$' \
  | grep -Ev '(^|/)(node_modules|dist|build|target|vendor|\.min\.|package-lock\.json|Cargo\.lock|pnpm-lock\.yaml|yarn\.lock)(/|$)' \
  | sort | uniq -c | sort -rn \
  | head -40
```

`--max-count=2000` bounds the walk to the 2000 newest commits in the window.
Deterministic, recency-biased, one process. Use this unless the window's *tail*
matters.

### Strategy B — even stride (representative across the window)

When you need the whole window represented (e.g. auditing a long-lived module's
history, not just its recent activity), sample every k-th commit:

```bash
K=$(( (C + 1999) / 2000 ))                           # ceil(C / 2000) → ~2000 samples
git rev-list --since="$WINDOW" HEAD \
  | awk -v k="$K" 'NR % k == 1' \
  | while IFS= read -r sha; do
      git show --no-renames --name-only --pretty=format: "$sha"
    done \
  | grep -v '^$' \
  | grep -Ev '(^|/)(node_modules|dist|build|target|vendor|\.min\.|package-lock\.json|Cargo\.lock|pnpm-lock\.yaml|yarn\.lock)(/|$)' \
  | sort | uniq -c | sort -rn \
  | head -40
```

`awk 'NR % k == 1'` takes a deterministic evenly-spaced sample (~2000 SHAs). More
processes than Strategy A (one `git show` per sampled commit) — heavier, so reserve
it for when tail coverage is worth the cost. Note the sample is of *commits*, so
counts are proportional, not absolute; rank is what you use, not the raw count.

## Directory rollup (wide repos)

When file-level churn fragments (a monorepo where every top file changed once),
roll up to a directory prefix to find active *areas*:

```bash
git log --since="$WINDOW" --no-renames --name-only --pretty=format: --max-count=2000 -- . \
  | grep -v '^$' \
  | grep -Ev '(^|/)(node_modules|dist|build|target|vendor)(/|$)' \
  | awk -F/ 'NF>=2 {print $1"/"$2} NF==1 {print $1}' \
  | sort | uniq -c | sort -rn \
  | head -40
```

`awk -F/ '{print $1"/"$2}'` collapses each path to its first two segments (tune to
1 or 3 per repo shape). The ranked areas then seed phase-2 hotspots/blast-radius
at the subsystem level. You can run file-level and rollup both and present each.

## Cross-platform counting fallback (Windows / no coreutils)

`sort | uniq -c | sort -rn` is fine on macOS/Linux/WSL/Git-Bash but not native
PowerShell. `git log` itself is cross-platform; only the counting pipe isn't.
Feed git's output to a stdlib Python counter (per the repo's cross-platform rule):

Save the counter below as `churn_count.py`, then pipe git's output through it —
NOT `python3 -` (in a pipe, stdin is git's output, so `-` would try to run that
output as the program):

```bash
git log --since="12.months" --no-renames --name-only --pretty=format: --max-count=2000 -- . \
  | python3 churn_count.py 40 2>/dev/null \
  || git log --since="12.months" --no-renames --name-only --pretty=format: --max-count=2000 -- . | python churn_count.py 40
```

with this counter saved as `churn_count.py`:

```python
import sys, collections, re
n = int(sys.argv[1]) if len(sys.argv) > 1 else 40
noise = re.compile(r'(^|/)(node_modules|dist|build|target|vendor|\.min\.|'
                   r'package-lock\.json|Cargo\.lock|pnpm-lock\.yaml|yarn\.lock)(/|$)')
counts = collections.Counter()
for line in sys.stdin:
    p = line.strip()
    if p and not noise.search(p):
        counts[p] += 1
for path, c in counts.most_common(n):
    sys.stdout.write("%6d  %s\n" % (c, path))
```

Same top-N cap, same noise filter, no coreutils dependency. The `--max-count` bound
still applies — Python counting an unbounded history would still be unbounded work.

## What phase 1 hands off

A ranked list of ≤N rows: `<count>  <path>` (or `<count>  <dir>/`). Carry it into
phase 2 — for each of the top paths, ask `wicked-garden-search` `blast-radius
<path>` and consult `hotspots` — and into the § Cross-reference 2×2. Do not treat
a high churn count as importance on its own: a generated file that changes every
commit tops this list and means nothing until the structural signal confirms (or
denies) that anything depends on it.

## Pitfalls

- **Streaming the full log.** The one thing this method exists to prevent. Always
  `--max-count`/sample above the threshold and always `head -N`.
- **`--follow` on a whole-tree scan.** It's per-path; it silently does the wrong
  thing here. Leave renames alone (`--no-renames`).
- **Counting merge commits' squashed diffs twice.** Add `--no-merges` if the repo
  merges heavily and you want first-parent-ish churn; state it if you do.
- **Trusting counts across strategies.** Strategy B counts are sample-proportional.
  Compare *ranks*, never raw counts, between a full-scan and a sampled run.
- **Forgetting the window is a knob.** 12 months is the default signal for "active
  now"; widen it to learn a mature system's long-lived churn, narrow it to learn
  what a team touched this quarter. Always report the window you used.
